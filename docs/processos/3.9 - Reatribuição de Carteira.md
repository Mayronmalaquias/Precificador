# 3.9 — Reatribuição de Carteira (imóveis/leads entre corretores)

## 1. Objetivo
Transferir o que está sob um corretor para outro quando ele sai/muda, mantendo carteira e
relacionamentos com o novo responsável.
- **Gatilho:** RH passa a informação para a Inteligência quando necessário.
- **Solicita:** gerente, RH ou diretor. **Executa:** Inteligência (via banco).

## 2. Regras de Negócio
- **Domínios que podem mover:** captação, **lead**, **visita**, **venda**, corretor, equipe, jornada de captação.
- **Vendas (exceção):** normalmente **NÃO se move** — só quando necessário ou **lançada errada** (correção).
  Mover histórico distorce ranking/comissão.
- **Identificação:** principal por **`id_corretor`** (`C61xxx`); também `id_gerente` e a **equipe do gerente**.
- **Cruzamento de equipe:** normalmente **não cruza**; exceção = **vendas em parceria** entre corretores de times diferentes.
- **Auditoria:** **não existe** hoje.

## 3. Fluxo
1. **Pedido:** RH informa → Inteligência **verifica no banco** (ids origem/destino, gerente/equipe).
2. **Execução:** por **`UPDATE`**, **manual** — **não há script** (ad-hoc a cada vez).
3. **Atualiza** cada domínio na **tabela respectiva** (captação, leads, visitas, jornada, equipe;
   venda só em exceção). Nas tabelas que guardam id **+** nome/team (ex.: `captacao`), atualizar os três juntos.
4. **Backup:** só o **backup padrão do banco** (não há backup por operação por padrão).

### Exemplo executado (captação) — Marcio→Lucas
```sql
-- backup antes (SELECT dos alvos) + transação
UPDATE captacao
   SET id_corretor='C61206', nome_corretor='Lucas Rodrigues da Silva'
 WHERE id_corretor='C61151';   -- 26 linhas; verificar rowcount == esperado antes do commit
```
> Padrão seguro aplicado: SELECT de backup → UPDATE em transação → conferir `rowcount` → commit.

## 4. Troubleshooting
| Sintoma | Causa | Situação / Ação |
|---|---|---|
| Moveu errado | Sem registro do que mudou | Descobrir manualmente — difícil |
| Erro ao atualizar | UPDATE manual | Pode falhar na execução |
| Move parcial | Esqueceu um domínio | Sem garantia → inconsistência |
| Venda movida errada | Impacto direto no ranking | Nunca pode estar errado; validar urgente |
| Rastreabilidade | Sem auditoria | Vai pela memória |

**Riscos (críticos):** manual · sem script · sem backup por operação · sem auditoria · memória.

## Perguntas em aberto / melhoria 🙋

2. Definir a **lista canônica de domínios** a mover (checklist) para evitar move parcial.
3. Regra formal de quando **venda** pode ser reatribuída (só correção de lançamento? parceria?).
