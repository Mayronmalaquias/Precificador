# 1.3 — Cadastro / Manutenção de Usuários (RH)

## 1. Objetivo
Manter o cadastro de usuários que sustenta **hierarquia de permissões**, **controle de
corretores por time**, **relatórios** e **controle de RH**.
- **Quem gerencia:** equipe da **Inteligência** (administrador) e os **assistentes**, pela aplicação web.
- **Ciclo de vida:** usuário existe enquanto um **gerente o mantém**; se para de desempenhar
  ou não alinha com as políticas, o gerente **solicita à Inteligência o desligamento**.
- **Liberação de login:** **não existe mais** — o usuário nasce `ativo=true`. O RH atua só no
  desligamento. Não há tela pública de "criar conta": só quem já está logado cadastra.

## 2. Regras de Negócio
- **Campos obrigatórios:** `username`, `password`, `nome`, `permissao`. **`team` é opcional** —
  administrativo/inteligência/estagiário não pertencem a time de corretor ("Sem equipe").
- **Permissões (7):** `corretor` · `estagiario` · `assistente` · `gerente` · `administrativo` ·
  `administrador` · `diretor`. Lista única em `frontend/src/components/rhFields.js`
  (`PERMISSOES`), consumida por Register, RHUsuarios e ControleCorretor — **não** repetir
  `<option>` hardcoded em tela nova.
  - `estagiario` tem **acesso base** (igual corretor no `AuthContext`), mas os filtros
    `permissao == "corretor"` de `ranking_service` e `rela_gerentes_service` **não** o pegam:
    estagiário não entra no ranking nem na contagem de corretores da equipe.
- **`id_usuarios`:** gerado automático no cadastro (próximo `C61xxx`); **único** no banco
  (`uq_usuarios_id_usuarios`).
- **`id_imoview`:** campo **"Código Imoview"** no formulário de cadastro (origem: aba
  "Corretores" do xlsx do AppSheet — `Corretor` + `Código Imoview`). **Único** — cadastro com
  código já usado devolve **409**. Sem ele o corretor **não aparece** no seletor do
  [[1.9 - Lançamento de Imóvel pelos Assistentes|Lançar Imóvel]].
- **Poderes por permissão:**
  - **Diretor / Administrativo (e administrador):** editam usuários, veem relatórios de **toda a
    empresa**, **desativam** / retiram acesso. Cadastram qualquer permissão.
  - **Assistente:** cadastra usuário novo (só **corretor / estagiario / assistente / gerente** —
    não cria administrativo, administrador nem diretor). Flag `podeCriarComoAssistente`.
  - **Gerente:** mantém os corretores do próprio time; preenche RH dos corretores ativos da equipe.
  - **Corretor:** acesso base.
- **Desativar** (soft) ≠ **Excluir** (delete físico) — ver Fluxo.

## 3. Fluxo
1. **Cadastro** — Inteligência ou assistente preenche os campos manualmente (`id_usuarios` é
   gerado automático: próximo `C61xxx`). *Implementação:* usuário nasce `ativo=true`,
   `status="Ativo"`, `desligado=false` → **já loga**.
2. ~~Liberação (RH)~~ — **removida**. `alterar-ativo` continua existindo só p/ desativar/reativar.
3. **Edição** — diretor/administrativo/administrador editam geral (`editar-usuario`);
   gerente preenche RH dos ativos do time (`editar-rh-gerente`); troca de time = `alterar-gerente`
   (muda o `team` para o do novo gerente).
4. **Desligamento** — gerente solicita → Inteligência desativa. *Implementação:*
   `alterar-ativo(false)` → `ativo=false` + `desligado=true` + `status="Inativo"`; usuário
   **permanece arquivado** (preserva histórico/relatórios). **Excluir** (`excluir-usuario`) =
   **delete físico**, uso de exceção.

## 4. Troubleshooting
| Sintoma | Causa | Situação / Ação |
|---|---|---|
| Não loga ("aguardando validação") | Usuário foi **desativado** | Cadastro novo já nasce ativo; ver `alterar-ativo` |
| Cadastro devolve 409 no Imoview | Código já é de outro corretor | Conferir a aba "Corretores" do xlsx / `usuarios.id_imoview` |
| Corretor não aparece no Lançar Imóvel | `id_imoview` vazio | Preencher via `editar-usuario` |
| `id_usuarios` duplicado | Código repetido | Sem colisão até hoje (campo único) |
| Desligado aparece no ranking | — | Nunca precisou; desativar já tira do ranking |
| Troca de gerente | `alterar-gerente` | Muda o nome do time para o do novo gerente |
| Exclusão por engano | delete físico | Puxar backup do banco (sem reversão automática) |

**Lacunas/riscos:** usuários **antigos** ainda podem estar sem `id_imoview` (só os do xlsx foram
semeados) → de-para manual no [[1.2 - Importação de planilhas de base|1.2]]; sem fila do RH, o
controle de quem entra é só a permissão de quem cadastra; exclusão física só reverte via backup.

## Atualização — Link de documentos no Drive (2026-08-11)

Campo novo no cadastro: **Documentos (link do Drive)** — `usuarios.link_documentos`
(Text, migration `20260811_link_documentos`).

- **É link, não upload.** Os arquivos continuam no Drive do RH; o sistema guarda só o
  endereço da pasta. Upload exigiria storage, política de retenção e controle de acesso
  a documento pessoal — outro projeto.
- **Onde aparece:** tela RH Usuários, largura total, antes dos campos de desligamento.
  Quando já há link salvo, aparece um botão **"Abrir ↗"** que abre em nova aba.
- **Quem edita:** mesma regra dos demais campos de RH — administrador/administrativo e
  o gerente pela tela de RH da equipe (`RH_CAMPOS_EDITAVEIS`).
- **Não é obrigatório:** ficou fora de `RH_REQUIRED_FIELDS`, então a ausência não conta
  como pendência de cadastro.

> ⚠️ O link aponta para documentos pessoais (CPF, RG, contrato). Quem tem acesso ao
> conteúdo é definido pela permissão da pasta **no Drive** — o sistema não controla isso,
> só guarda o endereço.

### Tipo de campo novo no formulário

`rhFields.js` ganhou o tipo `url`, renderizado em `RHUsuarios.js` como input + atalho de
abrir. Serve para qualquer campo de link que venha depois.

## Atualização — Validação de username duplicado (2026-08-17)

`cadastrar_usuario` **não checava** se o username já existia — e `usuarios.username`
**não tem UNIQUE**, nem no model (`String(100)`) nem no banco. Resultado: 7 usernames
duplicados na base, incluindo `admin` com duas contas.

Isso importa porque o `login()` casa pelo **primeiro registro que encontrar**: a pessoa podia
entrar com a permissão errada dependendo da ordem do banco.

**Correção** (`auth_service.cadastrar_usuario`), no mesmo padrão que já existia para o
`id_imoview` — `ValueError` → **409** pela rota, sem mexer em `auth_routes.py`:

```python
username = normalizar_user(username) or ""
if not username:
    raise ValueError("Username é obrigatório.")
em_uso = session.query(Usuarios.nome, Usuarios.id_usuarios).filter(
    func.lower(func.trim(Usuarios.username)) == username
).first()
if em_uso:
    raise ValueError(f"O username '{username}' já está em uso por {dono}. Escolha outro.")
```

Compara pelo username **normalizado** (`normalizar_user`: strip, espaço→`_`, lower, unidecode),
então `"Yasmin Nasser"`, `"yasmin nasser"` e `"YASMIN_NASSER"` são detectados como o mesmo.
`normalizar_user` é chamado de novo dentro do service (é idempotente) para o caso de alguém
chamar a função direto, sem passar pela rota.

Comportamento verificado:

```
'admin'               -> BLOQUEADO: já está em uso por 123456
'ADMIN' / ' Admin '   -> BLOQUEADO (caixa e espaços)
'Yasmin Nasser'       -> BLOQUEADO (vira yasmin_nasser)
'Fulano de Tal Silva' -> PASSA
''                    -> BLOQUEADO: Username é obrigatório
```

**Limitação:** isso cobre só o caminho da aplicação. Não protege de corrida entre requisições
simultâneas nem de escrita direta no banco — para isso falta o índice único, ver
[[_Registro - 2026-08-17]] §7.1.

**Não cobre a edição.** Se `/corretor/editar-usuario` permitir alterar username, a mesma
checagem é necessária lá — **não verificado**.

A limpeza dos 7 duplicados existentes está em
[[_Operação - Deduplicação de Usuários 2026-08]].
