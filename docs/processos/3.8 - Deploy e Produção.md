# 3.8 — Deploy e Produção

## 1. Objetivo
Publicar mudanças em produção com o mínimo de interrupção.
- **Infra:** 2 VMs separadas (front / back).
- **Domínio:** `inteligencia61imoveis.com.br` (HTTPS); back em `api.inteligencia61imoveis.com.br`.
- **Quem faz:** Inteligência.

## 2. Regras de Negócio
- **Branch de produção:** **`dev_miron`** (é dela que se faz `git pull`).
- **Front:** `npm run build` → **nginx** serve a pasta `build/`.
- **Back:** Gunicorn via systemd **`precificador`** (restart no deploy).
- **Migrations:** aplicadas **da máquina local** contra o **RDS**, **sob demanda**.
- **HTTPS:** renovação **automática** do certificado.

## 3. Fluxo
**Back (VM 1):**
1. `git pull origin dev_miron`
2. `sudo systemctl restart precificador`
   *(se `requirements.txt` mudou: entrar no virtualenv e `pip install -r requirements.txt`)*

**Front (VM 2):**
1. `git pull`
2. `npm run build` (nginx serve `build/`)

**Banco:** quando há migration nova → rodar `flask db upgrade` **local** apontando pro RDS.
**Ordem:** não há ordem específica. **Rollback:** nunca precisou.

## 4. Troubleshooting
| Sintoma | Situação / Ação |
|---|---|
| Deploy quebra produção | Corrigir na hora **ou** `git checkout` de um commit anterior que funcionava + restart |
| Cert HTTPS vence | Renovação automática |
| Rollback | Nunca testado |
| Dep nova | Entrar no virtualenv do back e `pip install` |
| Migration errada no RDS | Não coberto — sem `flask db downgrade` testado (ver [[1.5 - Backup e Recuperação]]) |

**Riscos/lacunas:** produção na branch `dev_miron` (branch única, sem `main` de release) ·
**sem monitoramento/healthcheck** (percebe no olho) · rollback nunca testado · migrations manuais
do local · Inteligência = ponto único.

## Perguntas em aberto / melhoria 🙋
1. **Monitoramento/healthcheck** (o back tem `/health`) + alerta de queda → entra no Nível 4.
2. **Testar rollback** (git + restart) e **`flask db downgrade`** uma vez.
3. Adotar **branch de release** (`main`) e/ou **CI/CD** para reduzir passos manuais e ponto único.
4. Documentar o passo a passo numa checklist fixa (evita esquecer `pip install`/migration).

## Atualizações (2026-08)

### Incidente: login 500 — `unsupported hash type scrypt` (hash x Werkzeug da VM)
- **Sintoma:** `sudo journalctl -u precificador` mostrando no login
  `ValueError: unsupported hash type scrypt:32768:8:1` (500 em `POST /auth/login`) — só para
  **alguns** usuários (os assistentes recém-criados + `miron`).
- **Causa:** o hash de senha foi gerado numa máquina com **Werkzeug novo (3.x)**, cujo default é
  **`scrypt`**, e gravado no **RDS compartilhado**. A **VM roda `Werkzeug==2.0.3`** (pin antigo),
  que **não sabe verificar scrypt** → estoura em vez de retornar "senha inválida". O banco é o
  mesmo p/ local e prod, então um seed rodado no local contamina a prod.
- **Correção (durável, não sobe Werkzeug na VM):**
  1. **Código** — forçar `pbkdf2:sha256` (default do 2.0.3, universal) em **todos** os pontos de
     hash: `auth_service.cadastrar_usuario` + alterar-senha, `usuarios_service` (editar),
     `seed_assistentes`. Nunca mais emite scrypt, mesmo rodando seed sob Werkzeug novo.
  2. **Dado** — re-hash dos 15 usuários scrypt no RDS p/ `pbkdf2:sha256` (14 assistentes com a
     senha real `61Imoveis`; `miron`, permissão nula e senha irrecuperável, resetado p/ `61Imoveis`
     — trocar depois). Vale **imediato** (é no banco, não precisa de deploy).
- **Diagnóstico rápido** (quem tem hash scrypt): `SELECT username FROM usuarios WHERE password LIKE 'scrypt:%';`
- **Regra:** senha **sempre** com `method="pbkdf2:sha256"` enquanto a VM estiver em Werkzeug 2.x.

### `requirements.txt` modernizado (stack Flask 3 / Werkzeug 3 / SQLAlchemy 2)
- Atualizado p/ as versões validadas no dev local: **Flask 3.0.3, Werkzeug 3.0.3, SQLAlchemy
  2.0.40, flask-restx 1.3.0, flask-sqlalchemy 3.1.1** + demais libs pinadas. Adicionado
  **`Unidecode`** (era usado em `helpers.normalizar_user` e **faltava**). `openai` é dead-dep
  (não usado). `scikit-learn` fica **comentado** (puxa scipy → quebra o boot).
- ⚠️ **É upgrade grande, não é só `git pull`:** `flask-restx 0.5→1.3`, `SQLAlchemy 1.4→2.0` e
  `flask-sqlalchemy 2.5→3.1` têm breaking changes. Na VM, com rollback pronto:
  ```bash
  cd ~/Precificador/backend && source venv/bin/activate
  pip freeze > requirements.lock.rollback      # backup p/ reverter
  pip install -r requirements.txt
  python -c "from app import create_app; create_app()"   # smoke: boota?
  # testar login + rankings + lançamento ANTES de confiar; depois: systemctl restart precificador
  ```
  Rollback: `pip install -r requirements.lock.rollback` + restart.
- Werkzeug 3 na VM torna o scrypt verificável de novo, mas o fix de hash acima **independe** disso
  (pbkdf2 roda em ambos) — mantê-lo mesmo após o upgrade.
