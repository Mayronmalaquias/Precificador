# 2.4 — Snapshot Diário e Evolução de Captação

> ⚠️ **Rascunho automático** inferido de `back-end/app/services/captacao_snapshot_service.py`.
> Validar cadência real do cron e quem dispara (ver "Perguntas em aberto").

## 1. Objetivo
Registrar **uma foto diária** do estado de todas as captações para montar as **séries de
evolução** (volume por equipe/corretor/bairro/endereço/categoria) no dashboard — algo que a
tabela `captacao` (só estado atual) não permite. Base do gráfico de evolução.

## 2. Regras de Negócio
- **1 linha por (dia, captação)** em `captacao_snapshot` (unique `data_snapshot+captacao_id`).
- **Idempotente:** `gerar_snapshot(dia)` apaga o snapshot do dia e regrava → rodar 2x no mesmo
  dia não duplica.
- **Backfill:** reconstrói o histórico de `created_at`→hoje; a **etapa** de cada dia é
  recuperada de `captacao_historico` (último evento com data ≤ dia); status via
  `data_fechamento`. Faz `TRUNCATE` antes → rodar **1x** para popular; depois o cron mantém.
- **Dimensões de série:** `equipe · corretor · bairro · endereco · categoria(etapa)`.
- **Normalização de chave:** agrupa variantes (sem acento, maiúsculas, espaços colapsados) —
  evita "Águas Claras" ≠ "AGUAS CLARAS". Métrica = `count(distinct captacao_id)`.
- **Top N:** mostra as `max_series` maiores; resto agregado em "Outros".

## 3. Fluxo
1. **Cron diário** chama `POST /captacoes/snapshot` (ou `gerar_snapshot`) → grava o dia.
2. **Dashboard** consulta `GET /captacoes/evolucao` (série) e `GET /captacoes/evolucao/opcoes`
   (dropdowns de equipe/corretor/bairro; se gerente, restringe à equipe).
3. **Backfill** rodado manualmente uma vez (ou quando precisar reconstruir o histórico).
4. Front: `CaptacaoEvolucao` (gráfico de linha).

## 4. Troubleshooting
| Sintoma | Causa provável (código) | Ação |
|---|---|---|
| Evolução sem o dia de hoje | Cron do dia não rodou | Disparar `gerar_snapshot` manual |
| Série "furada" no passado | Backfill não rodado / histórico incompleto | Rodar `backfill()` (TRUNCATE + rebuild) |
| Corretor duplicado na legenda | Variação de nome | Já normalizado por `_norm_key`; conferir origem em `captacao` |
| Etapa histórica aproximada | Backfill usa etapa vigente por `captacao_historico` | Esperado — é aproximação p/ o passado |

## Atualização — Cron quebrado e backfill (2026-08-07)

### O que aconteceu

O gráfico de evolução **congelou em 22/07/2026**. Diagnóstico:

```text
captacao_snapshot: min 2026-06-05 · max 2026-07-22 · 28.444 linhas
captacao         : última criada em 2026-08-07  (a operação nunca parou)
```

O cron **existia** na VM do back:

```cron
0 23 * * * curl -s -X POST http://localhost:5000/api/v1/captacoes/snapshot >/dev/null 2>&1
```

Quando a API foi fechada em **23/07** (`X-API-KEY`/JWT obrigatório), esse `curl` passou a
receber **401** — e o `>/dev/null 2>&1` engoliu o erro por 16 dias. A data bate exatamente com o
último snapshot gravado.

Confirmação na VM:

```bash
curl -s -o /dev/null -w '%{http_code}\n' -X POST http://localhost:5000/api/v1/captacoes/snapshot
# 401
```

### Correção

1. **Backfill** (`TRUNCATE` + rebuild a partir de `captacao` + `captacao_historico`):
   `{'ok': True, 'linhas': 41377}` — série de 05/06 a 07/08.
2. **Script dedicado** `backend/snapshot_diario.py`, chamado direto pelo venv — **sem HTTP e sem
   API key**, imune a esse tipo de quebra.
3. **Cron novo** (o `curl` morto foi removido):

```cron
50 2 * * * cd /home/ubuntu/Precificador/backend && venv/bin/python snapshot_diario.py >> /home/ubuntu/snapshot_diario.log 2>&1
```

Detalhes que importam — ver [[3.8 - Deploy e Produção]]:

- o `cd` é **obrigatório**: `app/config.py` usa `load_dotenv()` relativo ao cwd;
- log no `~`: o usuário `ubuntu` não escreve em `/var/log`, e redirect que falha impede o job;
- a VM roda em **UTC** — `50 2 * * *` = 23:50 de Brasília (fecha o dia local).

### Consumidor novo

O snapshot passou a alimentar também a leitura **"no período"** da Jornada na Visão do Diretor
([[2.14 - Visão do Diretor]] §6): quantos imóveis estiveram em cada etapa, somando quem já
estava antes do início do intervalo. Sem o snapshot, esse número vem vazio.

### Respostas às perguntas em aberto

- **Como o cron é agendado?** Crontab do usuário `ubuntu` na VM do back (`172.31.1.219`).
- **O backfill já rodou em produção?** Sim — 24/06 (carga inicial), 22/07 e **07/08/2026**.

## Atualização — Gráfico de evolução contava as encerradas (2026-08-17)

**Sintoma:** a curva só subia. Em 09/08 plotava **1.260** captações, sendo **298 fechadas**
(~24%). A captação encerrada continuava sendo fotografada todo dia e nunca saía do gráfico.

**Causa.** `_aplicar_filtros` só aplicava o status quando preenchido:

```python
if f.get("status"):
    q = q.filter(CaptacaoSnapshot.status == f["status"])
```

E o front abre com `status: ""` ("Status (todos)"), então nada era filtrado.

**Regra correta** (definida pelo time): a captação conta nos dias em que estava viva e **para
de contar a partir do dia do encerramento** — o passado dela na curva é preservado.

**O dado já estava certo.** O `status` do snapshot é gravado **por dia**:

```
dia ANTES do fechamento    ativo     3.545 linhas
dia >= fechamento          fechado   9.026 linhas
```

Então bastou excluir `fechado` na consulta — sem tocar no histórico, sem backfill:

```
captação encerrada em 15/07
2026-07-14  escolha  ativo     CONTA
2026-07-15  escolha  fechado   não conta
```

**Correções**
- Sem filtro explícito, a query exclui `STATUS_FECHADO` (constante nova no topo do service).
  Com filtro, respeita a escolha — `status=fechado` continua servindo para auditar.
- Dropdown do front corrigido: mostrava só "Ativo"/"Fechado", escondendo **`captado` (66)** e
  **`exclusividade` (53)**. Agora lista os quatro status reais, com o padrão em
  **"Em andamento (sem encerradas)"**.

**Efeito:** 1.260 → **962** em 09/08.

> `captado` e `exclusividade` **seguem contando** no padrão, por serem etapas vivas da jornada.
> Se para o time "captado" já encerra, é só somar em `STATUS_FECHADO`.
