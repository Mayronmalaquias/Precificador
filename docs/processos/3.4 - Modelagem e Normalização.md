# 3.4 — Modelagem e Normalização do Banco

> Plano completo e histórico em [[MAPA_BANCO]] e [[DIAGRAMA_BANCO]]. Para uma referência
> operacional das fontes de verdade atuais, ver [[3.15 - Mapa das Bases Atuais]].

## 1. Objetivo
Evoluir o schema (47 tabelas, 7 domínios) **sem perder dado**: normalizar identidade, unificar
pares novo×legado e criar integridade (FKs), de forma **aditiva e reversível**.

## 2. Regras de Negócio
- **Migrations** Alembic em `back-end/migrations/versions/` (`flask db upgrade`/`migrate`).
- **Princípio:** nunca dropar antes de (1) criar destino, (2) backfill, (3) validar contagem,
  (4) manter `*_legado` como arquivo bruto. FKs criadas `NOT VALID` e validadas depois.
- **Etapas do plano** (ver [[MAPA_BANCO]]): A identidade canônica · B vendas unificadas ·
  C trocar nome por id (FK) · D pessoas/dims redundantes · E isolar scraping (`imoveis` 7M).
- **Entregar views de leitura antes** de mexer na escrita (valida o de-para sem risco).

## 3. Fluxo
1. Mudança de schema → nova migration (revisar antes de aplicar).
2. Backfill + validação de contagem.
3. Criar FK `NOT VALID` → validar.
4. Manter fonte bruta (`*_legado`) intacta.

## 4. Troubleshooting
| Sintoma | Causa | Ação |
|---|---|---|
| Migration falha em prod | Divergência schema/dados | Revisar + `flask db upgrade` controlado |
| Join frágil | Falta de FK (relação por valor) | Ver relações tracejadas em [[DIAGRAMA_BANCO]] |
| Dado "perdido" após mudança | Drop prematuro | Restaurar de `*_legado`/backup |
