# 1.5 — Backup e Recuperação

## 1. Objetivo
Poder **reverter** um erro de dados sem perder o resto.
**Estado atual:** existe **só o backup do RDS**; **não há backup manual** antes de operações em
massa (reatribuição, dedup, full replace do `estudo_metricas`). Processo formal quase inexistente.

## 2. Regras de Negócio
- **Backup automático do RDS** (gerenciado AWS).
- **PITR ativado** (point-in-time recovery) — permite restaurar a um instante específico.
- **Segundo banco = standby Multi-AZ** (alta disponibilidade / failover).
- **`DB_HOST` = `db-restore.ctug6oqcsj14.us-east-2.rds.amazonaws.com`** (nome do host = "db-restore").
- **Backup efetivo p/ erro lógico hoje = semanal** (segundo o entendimento operacional).

> ⚠️ **Multi-AZ não protege contra erro lógico** (um `UPDATE` errado replica na hora pro standby).
> Cobre falha de infra/hardware. Para reverter dado errado vale o **PITR** ou o backup semanal.

## 3. Fluxo
- **Alta disponibilidade:** standby Multi-AZ assume automaticamente em falha de infra.
- **Erro de dados:** restaurar — hoje, na prática, o **backup semanal** (→ pode perder até ~7 dias
  de leads/visitas/captações). O **PITR permitiria voltar a minutos antes do erro** (subutilizado).
- **Restore:** nunca executado na prática.

## 4. Troubleshooting
| Sintoma | Situação atual |
|---|---|
| Erro grande de dados | Aceitável, mas perderia quantidade considerável de informação |
| Recuperação | Restaurar (semanal / PITR) |
| Restore testado? | Nunca → RTO desconhecido |
| Failover Multi-AZ | Nunca aconteceu, nunca testou |

**Riscos (críticos):** sem backup manual · restore nunca testado · janela de ~7 dias no semanal ·
PITR ativado mas fora do hábito.

## Perguntas em aberto / melhoria 🙋
1. **Padrão pré-operação destrutiva:** tirar **snapshot manual do RDS** + **backup por tabela**
   (SELECT → arquivo, como o JSON do Marcio→Lucas) antes de reatribuição/dedup/full replace.
2. **Testar um restore** (PITR e/ou snapshot) uma vez → medir RTO e validar que funciona.
3. **Usar PITR** como recuperação padrão de erro lógico (em vez do semanal) → RPO ~minutos.
4. Confirmar retenção dos automated backups (dias).
