# 2.1 — Dashboards do Gerente (BI)

> ⚠️ **Rascunho automático** inferido dos serviços de gerente. Validar acesso e fonte dos imóveis.

## 1. Objetivo
Consolidar, para o gerente/diretoria, a performance da equipe: imóveis, corretores, visitas,
clientes, ranking e evolução temporal. Front: `RelatorioGerente`, `VisitasEvolucao`,
`GestaoClientesVisitas`.

## 2. Regras de Negócio
- **Escopo por equipe:** o gerente vê a **própria equipe** (`id_gerente`/`team`); diretoria vê tudo.
- **Fonte:** lê do Postgres via `db_loaders` (formato compatível com as antigas abas do Sheets —
  ver [[2.6 - Sincronização com Planilhas]]).
- **Evolução de visitas:** dimensões `total · equipe · corretor · proposta · quartos · cliente ·
  imovel · tipo_captacao`; agrupamento `dia · semana · mes`.
- **PDFs** (corretor/gerente/equipe) reusam os helpers de Drive do `visita_service`
  (mesmo OAuth do [[1.4 - Relatório de Visita]]).
- **Gestão de clientes:** ações sobre cliente (`cliente_acao`) integradas ao dashboard.

## 3. Fluxo
Endpoints sob `/api/v1/gerente-dashboard`: `/dashboard`, `/imoveis`, `/corretores`, `/visitas`,
`/clientes`, `/ranking`, `/serie`, `/visitas/evolucao` (+`/opcoes`), `/visita/detalhe`,
`/gestao-clientes` (+`/acoes`, `/acoes/<id>`), `/equipes/dashboard`; PDFs: `/corretor/pdf`
(+`/download`), `/gerente/pdf` (+`/download`), `/equipes/pdf/download`.

## 4. Troubleshooting
| Sintoma | Causa provável | Ação |
|---|---|---|
| Gerente sem dados | `id_gerente`/`team` errado no cadastro | Ver [[1.3 - Cadastro de Usuários]] |
| PDF não gera | Token OAuth do Drive | Rerodar `ensure_oauth_token` |
| Números divergem do ranking | Fontes/regra diferentes | Cruzar com [[2.2 - Rankings]] |
| Corretor duplicado | Nome não normalizado | Ver de-para [[MAPA_BANCO]] |

## Atualizações (2026-07-28 → 07-31)

### Modelo gerente↔equipe é baseado em `team` (não no id do gerente)
- A equipe é identificada por `usuarios.team` (= `equipes.id_equipe`, ex. `G61017`). No modelo unificado (todos são `usuarios`; a **permissão** diferencia), **o `id_usuarios` do gerente pode ser ≠ do `team`** — ex.: Fernando Borges `id=C61134`, `team=G61017` (equipe "Alpha"). O gerente é o user com `permissao=gerente` cujo `team`=id_equipe (não há coluna gerente na tabela `equipes`).
- **Escopo da visão do gerente = `team`, não o id.** Corrigido em RelatorioGerente, GerenteRHCorretores (Controle Equipe), JornadaCaptacao e GestaoClientes — antes escopavam por id e gerente com id≠team via **0 corretores**. Backend: `retornar_lista(id_gerente)` e o dashboard filtram por `usuarios.team == id_gerente`. Visitas já seguiam o corretor (join no team atual, sem team denormalizado).
- **Dropdowns de gerente/equipe agora são dinâmicos** (tabela `equipes` via `GET /equipes` / EquipesContext) — acabou a lista fixa hardcoded (`gerentesFixos`) em RelatorioGerente e GestaoClientes. Filtros de equipe do diretor (Jornada, Gestão Clientes) usam a **lista mestra** → equipe nova aparece mesmo sem dado ainda.

### Criar equipe / novo gerente (fluxo alinhado)
- **Gerenciar Equipes**: ao criar, o **ID é automático** (padrão `G61xxx`, `proximo_id_equipe`) e você **escolhe o gerente** (dropdown de usuários) → `definir_gerente_equipe` seta `team=id_equipe` + `permissao=gerente` nele. Equipe e gerente saem alinhados.
- **Promover a gerente** (editar usuário) ou **registrar** gerente cria/garante a equipe do `team` dele — **só se não existir** (não renomeia equipe já cadastrada).
- **Diretor no Controle Equipe** (GerenteRH): acesso liberado + seletor de equipe (vê/gerencia RH de qualquer equipe; `solicitante_id` = id do diretor, que o back valida).

### Download de PDF via blob (auth)
- Downloads de PDF (gerente/corretor/equipe/visita/imóvel/cliente) vão por `fetch`→blob→anchor (`baixarArquivoApi`), o interceptor global injeta `X-API-KEY`. **Nunca** `window.open`/`<a download>` na URL da API — navegação do browser não leva o header → 401.

## Atualização (2026-08-05) — Motivo do "Sim" + flags de revisão do gerente

Objetivo: dar ao **diretor** um sinal, gravado no banco, de que o gerente **revisou** cada visita —
e permitir registrar o **porquê do "Sim"** (não só do "Talvez"). Vale em **RelatorioGerente** e
**GestaoClientesVisitas** ([[2.5 - Gestão de Clientes]]).

### Motivo do "Sim" (paralelo ao Motivo do "Talvez")
- Novo campo **`visitas.motivo_sim`** (Text), preenchido pelo gerente. Editado via
  `PUT /visitas/<id>` com `motivoSim` (igual ao `motivoTalvez`); também aceito no
  `registrar_visita`. Exposto em `db_loaders` como `Motivo_Sim`.
- **RelatorioGerente:** campo "Motivo do sim" no editar-visita, coluna na tabela, no detalhe e no
  export (xls + PDF). **GestaoClientes:** editor inline "Motivo do sim" (aparece quando a proposta
  normaliza p/ **sim**) + bloco "Motivos do sim" no resumo do cliente.

### Flags de revisão (banco, monotônicas, por visita)
- Tabela **`gerente_visita_visualizada`** ganhou **`viu_anexo` / `viu_notas` / `add_motivo`**
  (Boolean, default false). Antes só marcava "visto" (presença da linha).
- **Marcação automática na interação** (sem clique extra): abre o anexo → `viu_anexo`; abre as
  notas (audiodescrição) → `viu_notas`; salva um motivo (talvez/sim) → `add_motivo`. **Monotônicas**
  (uma vez `true`, ficam `true`). Gravadas sob o **gerente responsável** = `team` do corretor —
  mesma chave que o relatório do diretor consulta, então marcação numa página aparece na outra.
- **Endpoint:** `POST /visitas/vistas` aceita `viu_anexo/viu_notas/add_motivo`;
  `GET /visitas/vistas` devolve `ids` (compat) **+ `flags`** (mapa por visita). O
  `gestao-clientes` embute `flags` em cada visita (via `mapa_flags_por_visitas`).
- **UI:** badges **A / N / M** por visita (verde ✓ = feito, vermelho ! = pendente) nas duas telas +
  no export xls do RelatorioGerente. Serviço: `visita_vistas_service` (`marcar_visita_vista`,
  `mapa_visitas_vistas`, `mapa_flags_por_visitas`).
